# 阶段五平台需求：策略等价性与PTE运行验收

提出方：RSCH；日期：2026-10-22；依据代码：`6e8dd6f4`。

状态：供DEV评审及后续实施的需求提案。本次只交付需求，不代表已批准平台开发、正式冻结、模拟交易资格、部署或生产操作。本文不是新的研究检验结果，不修改已发布证据。

## 1. 业务目标

用户明确提出技术检验只有两个目的，RSCH认同，并按以下口径提出平台需求：

1. **行为等价：**选定StrategyCandidate与其冻结版本的实现，在声明的同一输入及执行条件下，产生一致的策略行为和经济结果。
2. **可部署、可运行：**对应发布包能够通过正常加载与身份认证，在指定版本的PTE中完成策略执行、账户记账及状态恢复。

身份、文件完整性、数据绑定、依赖与来源校验是上述目标的支撑。技术检验不重新搜索参数、选择候选、评判收益优劣或复算全部研究历史；不新增经济门槛，不改变既有交易规则。研究判断归RSCH，平台输出确定性事实和差异。

## 2. 对象及验收边界

| 对象 | 业务含义 |
| --- | --- |
| StrategyCandidate | 已登记、具有确定内容身份的候选及其实现 |
| StrategyVersion | 正式冻结版本记录，包含版本、来源、策略载荷与发布身份 |
| 版本发布包 | `strategies/<strategy_id>/releases/<version>/`中的源码、运行绑定和发布清单；这是本需求所称“冻结包” |
| StrategyRelease | 从版本记录构造的运行时表示，供SRT加载版本实现 |
| StrategyDeployment | 经认证的部署信息，关联发布包、运行绑定与部署回执 |

比较对象是候选运行行为与版本发布包运行行为，不是两个元数据对象的字段相等。源码相等不能单独证明行为等价。SRT部署成功也不能单独证明PTE可运行。

冻结前使用“拟冻结发布包”，并明确它不是已正式冻结的版本。受检对象应使用拟定的最终版本身份和完整发布材料；任何测试专用授权或部署凭据只属于隔离测试空间。

## 3. RSCH调用流程及输入

以一次面向选定候选的技术检验业务请求组织两项目标，内部可分步骤运行。优先改造现有公共入口，不要求新建独立平台、通用工作流系统或大量接口。

RSCH显式提供：

- 候选登记与内容身份、实际选型决定及选型交付引用。
- 拟定版本、父版本、冻结计划，以及原评价的明确证据引用。
- 已获准的数据资产与输入绑定、评价窗口和预热范围、初始账户、费用、价格与成交规则。
- 事前声明的比较字段、容差、回放场景、PTE运行环境和资源预算。

平台负责检查强类型契约、身份一致性和数据时间边界；RSCH负责研究范围、场景充分性及授权。不得从报告自然语言推断用户批准，也不得读取无关研究批次或未授权的新样本。

建议业务顺序：核对输入与准备包 → 行为等价检验 → 隔离PTE检验 → 发布两项结论及精确受检对象 → 用户审批冻结 → 冻结事务核对受检内容与最终包。

## 4. 需求A：行为等价

### A1. 同条件运行

候选与拟冻结实现使用同一份已认证的数据、可用时间、日历、参数、初始资金和持仓、费用及交易规则。必须通过各自正常SRT加载入口执行，发布包不得借用研究工作区的候选源码或隐式导入路径。

保留原评价 → 当前候选 → 拟冻结实现的对应关系：先确认当前候选可以复现声明的原结果，再确认拟冻结实现与候选等价。只重放事前指定的原账户场景，不重跑候选全集和阶段四搜索。

### A2. 比较内容

至少比较策略声明中实际使用的：

- 输入内容身份、时间覆盖和数据可用截止点。
- 信号、决策、目标仓位或目标份额、订单方向与价格数量规则。
- 持仓周期、持有年龄等影响后续决策的状态。
- 在同一历史执行条件下的成交、费用、现金、持仓及净值。

身份、方向、数量和离散状态要求精确一致。浮点字段允许使用协议事前声明的容差；默认零容差，不得失败后自动放宽。运行ID等非经济字段可以排除，但排除列表须显式留证，不能排除时间、方向、数量或影响后续决策的字段。

### A3. 差异输出

返回检查范围、实际覆盖、双方身份、首个差异位置、字段及双方值，并关联必要的完整差异证据。数据缺失、异常退出、未覆盖场景不能计为通过。有限回放只支持声明场景内的等价性结论，不输出对任意未来输入的普遍证明。

## 5. 需求B：发布包与PTE集成验收

### B1. 冻结前可检验，生产门槛不变

提供隔离的测试注册表、发布包根、数据空间、账户数据库及渠道替身，全部置于仓库`.tmp/`下；正式结果另通过公共证据接口保留。测试不得访问生产配置、账户或渠道，不建立真实Futu连接，不产生外部委托。

测试需调用PTE的实际加载、账户准备、决策、订单处理和持久化代码。可替换时钟、外部数据获取和券商边界，不能替换待验收的策略/PTE业务逻辑，不能通过猴子补丁跳过认证。隔离测试所需的版本、资格与部署记录应明确标记测试身份并局限于测试根；正常PTE仍只接受已冻结、已部署且具备PAPER_READY资格的版本。

当前缺少该能力时必须报告未完成，不能用历史执行器代替PTE后宣称通过。DEV须在设计中说明测试记录如何构造、如何确保测试凭据不能被生产接受。

### B2. 包与环境

校验版本、包清单、源码、依赖、运行绑定和部署引用的一致性；缺失、篡改、多余文件或不支持的契约须明确失败。受检环境不能依赖实验目录可导入。记录实际平台提交/构建身份、Python及关键依赖、PTE/SRT契约和有效配置。

只声称通过被测环境的验收。生产运行版本不同，需要明确兼容检查或在目标版本重验，不能以工作区最新代码代替生产事实。

### B3. 最小PTE运行场景

| 场景 | 必须观测到的结果 |
| --- | --- |
| 加载及账户准备 | 正常资格和部署认证、输入绑定、数据准备、策略初始化完成 |
| 入场、持有、退出 | 经PTE正常业务入口推进决策和执行时点，生成符合策略合同的计划与订单；接收模拟回报并正确记账 |
| 未成交或部分成交 | 意图与实际持仓分离，按明确成交增量更新账户；再次决策符合策略声明的补齐、撤销或保持规则 |
| 重复请求及重复回报 | 复用原决策/订单事实，无重复下单或重复记账 |
| 重启恢复 | 在存在持仓或未完成订单时重启，恢复原绑定和账户状态，继续执行结果与不中断路径一致 |
| 必要失败路径 | 包损坏、输入缺失或晚于决策时点、渠道结果未知时明确失败或待对账，阻止不应产生的新单 |

平台提供确定性场景和断言能力；RSCH按候选合同选择覆盖，不要求每个候选重复整个平台测试全集。对多档位策略增加加仓、减仓和目标变更场景；不支持或不适用须说明原因及覆盖影响，不能默认为通过。

使用已有获准数据或明确标记的合成输入、受控时钟和渠道回报，无需等待自然交易日。核对T日决策、T+1执行等时序。渠道替身提供的回报不证明真实流动性，也不要求PTE回报账本无条件等于TXE的历史成交模型；相同成交事实下的费用和账户状态必须符合共同合同。

PTE运行验收不包括长期收益观察、真实券商连通性或生产服务健康保证。这些结论应由相应运行事实单独支持。

## 6. 冻结前后的一致性

检验报告绑定候选内容、计划、受检发布内容、环境与数据身份。审批对象明确引用该报告及精确计划；正式冻结仍须用户批准。

冻结事务验证最终包与受检源码、载荷、依赖和运行绑定一致，并验证最终清单和版本身份。若最终格式含审批/事务等后生成元数据，须显式定义允许变化的字段及其映射，分别记录受检内容哈希和最终包哈希；不得把计划哈希当作发布包哈希，也不得宽泛忽略所有元数据。

代码、参数、依赖、执行合同或其他影响行为的内容变化，相关检验结论失效；不得沿用原PASS。只要可证明最终发布内容就是已检验内容，冻结时无需再次重放所有账户。正式冻结、资格授予、SRT部署和PTE启用分别记录状态，不因测试通过自动发生。

## 7. 证据、状态与收尾

### C1. 明确报告两项目标

分别返回行为等价与PTE运行验收的结果，附范围、环境、证据及失败原因。至少区分通过、失败、未执行、执行未完成；单项不适用另附理由。两项所需检查全部完成并通过，才能给出技术检验整体PASS。

技术结论、证据发布状态、冻结状态、正式部署状态和PTE启用状态独立呈现。发布失败时保留已完成的计算事实并明确未形成正式交付；部分完成或工具调用成功不能包装成整体成功。

### C2. 正式证据

通过现有公共证据与交付接口保存受检对象、场景、实际断言、差异、环境、输入引用和计时。只有摘要文字或临时目录不能构成正式验收证据。已有发布原件不改写，新结论使用新证据和新修订。

账户计数与研究概览须识别合法证据布局和记录类型，接受技术检验产生的`inspection/`等受管结构。不得把检验辅助记录计成研究候选或绩效账户，也不得为容忍目录而吞掉未知或损坏记录；识别失败应返回可定位的状态。

## 8. 性能与可观测性

### D1. 认证范围和复用

常规技术检验聚焦选定候选、所选原账户、直接输入、发布内容及其必要依赖。选型交付引用仍需核对身份和成员关系，但不应为每个后续动作重新解码或复算无关候选、全部账户和整段研究历史。

对历史交付的来源与完整性仍须有可解释的认证依据。DEV提出最小可信校验边界及复用方案；跨调用复用必须说明不可变对象、认证版本、失效条件和使用时内容变化的处理。不能只凭路径、文件存在或一次历史PASS判为当前有效。若现有存储不能保证安全复用，应明确所需最小格式/存储变更，不以放松完整性换速度。

完整历史档案审计可保留为显式操作；不得在选型、检验、发布和概览中反复隐式执行同一重型认证。并行不是验收前提，先消除无关和重复工作。

### D2. 测量和进度

- 记录准备、读取与认证、重放、PTE场景、证据写入、发布及收尾的分段耗时和总耗时。
- 报告文件/字节读取量、认证调用次数、复用命中、峰值内存及并发配置；可证明实际工作范围。
- 长步骤至少每30秒输出当前步骤、已完成工作量和耗时；未知总量不得伪造百分比。
- 支持显式资源预算与取消；中断保留诊断，不发布虚假PASS，不留下会继续外发订单的测试进程。

性能验收必须覆盖用户感知的完整调用链。采用相同机器、输入、版本及并发条件比较冷/热运行，记录重复次数，不用单次文件时间差当正式基准。预期：所选候选和证据不变时，增加无关候选及历史账户不增加策略重放数，也不触发逐个解码其账本；相同受检内容不在每个入口重复执行全链重型认证。

本提案不凭估计指定分钟数硬门。DEV先提交完整链路基线、明确工作量和可验收的耗时/内存预算；RSCH评审是否满足日常研究使用。交付须给出实际前后数据及余留成本。

## 9. DEV聚焦验收矩阵

| 编号 | 验收要求 |

| T2 | 输入内容、时间或初始账户不同明确拒绝；非经济运行身份差异按显式规则处理 |

优先聚焦变更链路和负向边界；仓库级全量回归由用户另行要求。DEV按风险选择必要既有契约测试，不以测试数量代替业务验收。若影响既有冻结发布或生产运行格式，应先说明影响和迁移需求，不自动重写历史发布。

## 10. S015现状与后续补验

现有[INSPECTION/1](deliveries/INSPECTION/1/report.md)的8项PASS是原范围内的真实结果：C0031与拟冻结实现完成两种费用场景、各434个交易日的技术比较，容差0。它未执行PTE部署与运行链路，因此不能直接映射为本需求的整体PASS。

DEV实施验收后，RSCH使用新增能力为同一候选形成新的检验修订，补齐PTE证据，判断哪些既有检查可在身份一致时复用；不修改原报告或伪造历史PTE通过。不扩大行情范围、不重新选型、不自动批准冻结。

本轮观察的性能与收尾问题见[HANDOFF](HANDOFF.md)及[概览失败记录](experiments/EX006_20261022/others/overview_failure.json)：选型、检验及发布入口各有约17至18分钟的历史认证开销，发布耗时约1033.613秒，末期进程内存观测约25GB。检验主体首末证据时间间隔约10.18秒，仅是定位线索，不是性能基准。

建议DEV实施顺序：先评审两项验收契约及隔离PTE方案，再补齐运行检验、受检内容到最终包的绑定，最后完成认证范围/复用优化、概览修复及完整链路测量。可按依赖并行开发，最终以同一业务请求的真实结果验收。

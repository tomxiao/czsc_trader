## 3. 最小模块、契约与 API 方案

### 3.1 DFLS 产品与 PTE 宿主装配

复用 ProviderKey、SourceRef、ProviderConfig.equity_bindings 及现有 prepare/fetch，不新增另一套行情读取或调度框架。
宿主增加版本化的强类型来源配置，声明市场、产品、准确 SourceRef、受支持适配器、交易时段及规则版本。
配置不携带任意 Python 导入入口；凭据留在现有环境配置。报价连接由宿主统一创建、共享和关闭，正常服务及离线维护使用同一装配入口。

- CN：复用已有 Tushare RAW/HFQ 行情读取；独立交易日历；按生效日给出交易单位、价格步长、涨跌停与可交易事实；补齐适用资产的分红、拆并份及支付时间证据。
- US：复用 Futu RAW/HFQ 行情和 RTH 日历，保留纽约时区、夏令时及提前收市；补实际交易约束及现金分红支付证据。
- 公司行动明确区分“已确认区间无事件”和“未取得资料”；不能把研究期 NONE 延伸到未来，也不能把除息日当支付日。找不到可靠来源时返回明确缺口，阻断相关账户准备。
- 研究用 Tradable=True、缺失条视为不可交易等假设不直接成为生产事实。正式数据的可用时间和事件生效时间分别保存。
- 价格继续后复权用于信号，未复权用于订单、成交、费用和估值；分红、拆股按真实数量与现金事件处理。

现金分红支付日、当前限制及信息可用时间的具体上游字段需在实施首步完成真实取源验证；现有 adapter 本身不能证明这些产品已就绪。

| 版本 | 必须覆盖的输入 |
| --- | --- |
| S001-v1/v2 | 588080 RAW 日线；HFQ 日线、30 分钟、完整周；规范历史起点 2020-11-16 |
| S002-v1 | 510500 RAW 日线、至少 300 条 HFQ 日线；保留包但不启用退休账户 |
| S003-v1 | 510500 RAW 日线与 M30 执行报价；固定 seed；中证500月末权重及个股资金流增量 |
| S007-v1 | 588080 RAW/HFQ 日线；固定 seed、Shibor、创业板指标、ETF份额、SPX |
| S011-v1 | 159326 RAW 日线、HFQ 日线/M30；沪深300成交额、SPX |
| S015-v1 | 159326 RAW/HFQ 日线及 RAW M30；保留用日线比例把 M30 中心映射至 HFQ 尺度的原规则 |
| S018-v1 | MU RAW 日线，MU/SOXX HFQ 日线；US 日历、限制及公司行动 |

八个版本的 decision_clock 均为 DAILY。S003 的 M30 是执行报价输入，S011/S015 的 M30 是观察输入；本次不扩大为自动 M30 策略调度。

复用 [FormalV4Inputs、register_recipe](../packages/paper_trading_engine/src/paper_trading_engine/formal_v4_advice.py) 的每日前推和区间身份固定能力。
主交易产品的 SourceRef 可在生产配方中显式选择；冻结辅助/执行输入内的 SourceRef 若需改变取源或可用性合同，必须由 RSCH 通过正式输入/同版本升级流程处理。
同名来源只允许相同合同，不能把留存 callback 悄悄换成语义不同的实时来源；历史证据和哈希不改写。

### 3.2 通用账户重绑

升级现有 `update_account_bindings` 公共入口。V4 请求使用明确的强类型契约，包含账户与渠道身份、预期当前发布哈希、目标版本及发布哈希、切换生效区间、原账户事实指纹、目标 `EquityAccountRules`、正式输入配方引用和状态处理方式。旧请求与 V4 请求按类型分流。

| 场景 | 状态处理 |
| --- | --- |
| 旧合同 → V4 | 按真实账本及经复核的策略字段映射构造 V4 状态 |
| V4 → V4，状态与执行合同兼容 | 沿用当前持仓周期、预算、可卖锁、事件游标及策略状态值，保持状态修订号单调递增，按目标发布身份重建状态绑定。适用于同版本新哈希和同策略族已批准的后继版本 |
| V4 → V4，状态合同或私有字段语义变化 | 提供针对精确新旧身份的显式状态映射，由 RSCH 复核私有字段含义。平台校验目标状态合同与账户事实一致，无法确认兼容时拒绝重绑 |

结构一致只是兼容检查的一部分。重绑同时核对目标冻结包的资格、标的、市场、币种、渠道归属、执行规则和输入配方。若同一发布仅更换供数配方，使用既有 `bind-recipe` 流程并从新执行区间生效。

状态材料使用现有 AccountStrategyState、PositionCycle、CycleBudget 及可卖锁类型，保存来源成交、账本和原周期引用：

- 平台负责现金、冻结现金、应收、持仓、成交周期和可卖事实；全部历史订单、成交、决策、快照、初始资本和 observation_start 保留。
- RSCH 明确策略私有字段映射。当前 S003 的 core_quantity=5900、S007 的 locked_quantity=63300/had_position=true 是待最终快照复核的映射，不硬编码到平台。
- 持仓入场时点、累计买入成本、卖出收入、费用及剩余数量来自真实账本；不能用回测重算替代真实成交，也不能为迁移强制平仓。
- 空仓账户仍检查旧周期与未终结意图；不能仅凭 quantity=0 丢弃尚未完成的预算或待确认结果。
- 迁移明确保存事件处理边界，避免启动后重复计入既有分红、支付或拆股。资格按目标精确发布身份单独批准。

准备和映射在写事务外显式完成，应用阶段只做身份、状态、余额及并发变更检查，不隐式复算整段策略历史。
持有数据库单写锁，最终事务再次比较原事实指纹；全部目标账户一并提交，任一失败均不切换绑定。
配方先写不可变记录、校验哈希，事务内引用该记录；活动索引须有可恢复的发布步骤，避免 SQLite 与文件半提交。
提交时保存新旧发布身份、状态处理方式、输入配方和生效区间。结果明确返回 COMMITTED、相同计划的 ALREADY_APPLIED 或具体失败。账户保持暂停，由获准的恢复操作启用。

绑定切换从满足目标冻结约定且晚于最后已采纳区间的首个可执行区间生效。保留原区间的决策、输入与发布身份，以原执行边界阻止重放。新发布首次调度从该边界继续，按目标身份计算新决策。未终结渠道订单、未知成交、未解释冻结资金、错误旧哈希或状态不一致均拒绝重绑。

### 3.3 发布与只准备数据

构建认证复用 SRT 的原生 V4 发布包/部署读取能力，核对闭包和定义，不要求原生源码伪装成旧 SRT 类目录。
发布 verify 按实际冻结合同及账户规则检查 CN/US，保持只读，不授予资格、不联网重做策略回测。

维护数据准备复用现有 DFLS 与 V4 配方组装，在公共账户准备入口补明确的 V4 只准备分支：给定账户、目标输入区间和真实 as_of，返回准备引用和逐产品状态，不生成/采纳决策、不提交订单。
不能通过伪造 observed_at 绕过 prepare_interval 的实时执行时窗约束；历史故障重跑与下一执行区间的生产准备分别记录。
S003 原失败区间 2025-09-04 至 2026-11-05 的14份权重快照继续按既有月末契约验证，并单独记录数据准备结果；账户周期恢复由后续调度事实证明。

## 4. 实施与验证顺序

1. 先完成双市场真实供数验证、来源装配及发布构建/只读预检分流。
2. 再完成通用重绑接口与只准备入口，覆盖首次迁入 V4 及已运行 V4 账户的后续重绑。RSCH 提供私有状态映射。需要改冻结 SourceRef 的版本由 RSCH 正式处理并保留等价证据。
3. 在工作区临时目录用生产一致性副本演练 schema 6→8、六个账户迁移、S018创建、输入准备、重启及回退。生产副本隔离真实下单通道。
4. 交付精确源配置、迁移清单、新发布身份、测试结果和待批准的生产操作。历史测试通过不替代此次缺口验证，也不自动新增研究绩效门槛。

最小聚焦覆盖：真实八包构建认证；CN/US 正式宿主装配到准备/决策；缺源与错 revision；CN 假日完整周、涨跌停/停牌、US 夏令时/半日市/RTH；现金分红支付及拆股；S003 DAILY+M30 执行与 seed/增量；S015尺度映射；重复启动复用已采用输入。
重绑覆盖已有持仓、空仓、退休账户不变、未终结/未知订单拒绝、旧哈希错误、批量原子性、重复应用、配方文件提交中断恢复、现金与持仓不变及首次新决策延续。用 CN/US 测试验证已运行的 V4 账户可再次重绑，并覆盖同版本新哈希、兼容后继版本、显式状态映射、状态不兼容拒绝和旧区间禁止重放。
实施结果按上述聚焦范围验收，仓库级回归按用户单独要求执行。

## 5. 一次停机维护的发布步骤

实施验收后再确定维护窗口，须在 CN/US 策略所用时段之外，且无未终结订单。无需预设日程或停机时长；由副本演练估算停机计算量，耗时的数据下载尽量提前完成。

1. 用户批准后，对拟启用的六个现有账户对应版本及 S018 的精确哈希授予 PAPER_READY，复用 deploy_strategy 生成/核验部署凭据。S002保持退休。
2. 固定干净提交，获准后合并、打附注 tag（暂建议 v0.6.22）、推送并构建。构建须覆盖新 DFLS、PTE、SRT及准确策略快照。
3. 再次核对各渠道订单、成交、持仓和现金；暂停目标账户，停止 WDG并确认写进程退出。保存原账户运行状态。
4. 一致性备份数据库、共享配置、活动发布指针、账户/输入绑定数据。停服前备份点作为全套恢复基准。
5. 使用低阶 pte-release publish 安装制品并保持服务停止；用目标发布解释器执行 schema 6→8，再通过通用重绑接口按迁移清单完成账户状态与配方绑定。
6. 明确注册原 CN 渠道配置和新 US 渠道；保留原 CN 资金。使用 channel create-v4 创建暂停的 S018，再 bind-recipe。S018保持冻结 RTH 时段；模拟账户ID、USD资本、S018初始资本、模型费率和费用归因边界须进入最终批准清单，不能照抄文档示例。
7. 单独执行 S003 历史故障区间的数据准备，并准备各账户下一执行所需输入。完成修复后的 pte-release verify，随后 activate，再启动WDG；此时全部目标账户仍暂停。
8. 核验目标版本、HTTP/WDG健康、schema、账户身份和真实余额、周期状态、输入来源及两渠道对账。按授权分别恢复渠道和策略账户，S002保持退休。
9. 后续首轮调度记录准备、决策、订单和对账结果；只准备成功不能宣称完整账户周期成功。控制台不改造，US使用CLI与审计查看。

上述低阶命令复用 [运维手册](PTE_OPERATIONS.md)，生产根目录由 scripts/pte-publish.ps1 的配置确定。
现有一键脚本自动 verify/deploy/restart，不用于此次需要中途迁移账户的维护；使用明确分步命令，不弱化校验。

## 6. 回退与授权边界

如维护验证失败，只有尚未提交任何新渠道订单，或所有新订单均已确认终结、零成交且现金与持仓对账一致，才可停服并恢复同一维护点的数据库、配置/活动输入索引和活动版本指针，再用旧版本验证后恢复服务。
schema 8 与新账户哈希不允许只切旧代码而复用新数据库。存在活动或结果未知的新订单，或新版本已产生成交时，先阻止新单并对齐渠道事实，不直接恢复旧账本；“尚未观察到成交”不代表可以丢弃订单归属。

建议下一步批准当前分支上的 DEV 实施、双市场聚焦测试和相关模块文档更新，并在所需节点由 RSCH完成显式状态映射/来源迁移。
生产写入、运行资格授予、合并/tag/推送、停服、渠道资本配置、S018生效与账户恢复不包含在本次评审内，待形成精确制品与迁移清单后再确认。

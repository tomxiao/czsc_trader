# 测试治理指南

本指南面向 DEV 和测试维护者，以最低持续成本保护关键业务风险，适用于个人量化团队（OPC）。
测试的价值是及时发现有实际影响的缺陷；用例数量、覆盖率和流程完整程度都不是独立目标。
模块边界见 [DEV 工作指南](DEV_AGENT.md)，生产验收见 [PTE 运维手册](PTE_OPERATIONS.md)。

## 1. 验证范围与时间预算

| 场景 | 验证范围 | 时间预算 |
| --- | --- | --- |
| 常规功能修改或缺陷修复 | 受影响行为及必要的跨模块契约，使用最小聚焦集合 | 不超过 30 秒 |
| 用户要求的完整离线回归 | 全部在用模块的关键契约、必要集成链路、发布验收、前端测试及静态检查 | 不超过 200 秒 |
| 纯文档修改 | 内容、相对链接和差异检查 | 不运行功能回归 |
| 在线渠道、服务或真实研究复验 | 按单独授权的目标和范围执行 | 按任务约定，不混入离线回归 |

预算计入入口启动、测试收集、夹具准备、执行、子进程、清理和结果汇总的墙钟时间。
比较时记录代码版本、执行范围、机器与并发配置、缓存条件及明显的外部负载；累计用例耗时不能代替端到端耗时。
失败、中断或环境异常的运行可用于诊断，不作为完成验收或稳定性能基线。

超预算时先定位成本并优化；功能通过与效率达标分别报告。确有必要的昂贵专项说明独立风险、耗时和触发条件，
但不得仅将慢测试移出完整集合、更名、跳过或缩小已约定范围来宣称达标。调整验收范围或预算须由用户确认。
不为满足预算终止尚未完成的必要验证并报告成功；也不为测量性能擅自反复运行全仓回归。

完整回归记录实际耗时及与 200 秒预算的对照，供测试治理使用。功能及收集完整性通过时返回退出码 0，
失败时返回 1。耗时仅作为观察项。

## 2. 在成本最低的有效层级验证

| 层级 | 主要职责 | 执行要求 |
| --- | --- | --- |
| 模块契约与计算 | 输入类型、数值边界、状态转换、持久化及失败语义 | 使用最小合法输入，在行为所属模块验证；不附带无关上游流程 |
| 跨模块集成 | 类型投影、身份传递、调用衔接、事务与恢复 | 真实执行被测边界，复用目标之外的已验证准备结果 |
| 端到端 | 证明关键主链能贯通并产生正确业务结果 | 保留少量代表场景及必要异常，不重复各模块全部参数矩阵 |
| 真实发布与在线验收 | 核验实际制品、配置、渠道及部署环境 | 与合成功能测试分别报告；在线操作遵守生产授权 |

公开 API 测试不等于每次从取数、回放、检验、冻结开始完整重演。
被测目标之外的依赖可以使用固定输入、可信不可变种子或契约边界替身；目标行为及其必要跨模块衔接必须真实执行。
例如测试报告指标的传递时，可复用已验证的冻结包；测试冻结过程时，则必须实际执行冻结及相应失败路径。
数据库事务、进程终止或并发竞争本身是目标时，不能用内存替身或模拟返回替代。

每项关键风险确定主要承接位置：DFLS 负责数据，SRT 负责策略运行，EC 负责执行与账户，SE 负责数值评价，
SM 负责身份和生命周期，SC 负责图表契约，TDR/PTE 负责宿主编排与跨模块衔接（含 PTE 的 WDG）。
同一风险不因经过多个宿主、接口或市场就重复整套测试；额外测试须保护实际不同的契约或行为。
A 股、美股的交易规则、日历、币种及渠道绑定差异分别覆盖，共用算法的等价输入不重复展开。

资金、订单、成交、身份、不可变证据、因果时点及失败恢复等关键风险必须有有效覆盖。
平台测试验证实现和契约，不评价研究结论、选型质量或策略盈利能力，不重算历史候选全集。

## 3. 用例准入、收敛与删除

新增长期用例必须同时说明：保护什么独立风险、现有用例为何不能承载、为何选择该层级，以及新增准备和执行成本。
小改在提交说明中简述即可，不新增治理表单、平台状态机或专用审批流程。
优先复用合适场景与夹具，但不将无关行为拼成难以诊断、必须整体重跑的巨大用例。

临时 TDD 用例用于复现和修复问题；完成后合入适合的长期场景，或作为独立风险用例保留。
尚未收敛的临时用例标记 `TEMP-TDD`；功能交付时处理，不默认永久积累。
低影响、可逆且没有独立业务风险的修改，不为镜像实现而新增测试。

删除或替换用例有三种合理依据：

- **风险仍重要，但覆盖重复：** 指明继续承接的用例或层级，保留关键断言并删除重复执行。
- **业务或接口已退役：** 删除对应场景与夹具；仅保留当前仍承担的历史完整性或迁移契约测试。
- **验证价值低于持续成本：** 说明剩余风险与取舍，可直接删除，无须为了保住旧断言另造用例；不得因此移除必要的关键风险覆盖。

同一风险的等价参数可以合并；不同业务分支、单位、时点和关键阈值按实际差异保留。
需要独立定位的参数使用清晰节点；确需共享状态的交互序列和数学参考计算可使用循环，但失败必须指出具体输入。
不以把参数化改成循环、合并函数或迁移目录作为降本成果，成本以实际准备与执行为准。

较大范围的存量治理按以下步骤进行，日常小改沿用本节准入规则即可：

1. **先定场景，再替换用例。** 从现行契约和真实失败后果列出独立场景，为每项记录承接层级、关键断言和必要资源。展开参数及前端场景，形成可对照的节点预算。
2. **按场景重建。** 能由模块小样本证明的风险留在模块层，宿主保留真实衔接和少量完整生命周期。替代场景通过后删除重复的旧参数矩阵，并清理无调用者的夹具与辅助代码。
3. **核对场景与收集结果。** 用实际收集的节点核对场景承接。一个生命周期可覆盖多个相连的风险，同一执行节点只计一次。发现清单漏掉独立风险时逐项补列理由和节点，说明实际数量与预算的差异。

## 4. 夹具、数据与执行成本

- 合成数据只覆盖目标所需的窗口和边界。减少数据不能改变因果关系、缺失位置、交易规则或目标失败原因。
- 昂贵不可变种子按实际复用范围建立一次；消费者使用隔离的可变副本。避免每个文件或参数节点重复取数、回放、检验、冻结、扫描源码或创建仓库。
- 种子的建立、加载和复制也计入预算。身份与哈希保持真实，必要路径正确重定位；不能用共享可变状态、伪造身份或隐藏陈旧缓存换取速度。
- 单连接业务计算可使用真实 SQLite 内存库；持久化、重启、迁移、跨连接及落盘事务验证使用独立文件库。仅复用目标之外的空库或账户种子，正常打开和身份校验仍须执行。
- 至少有代表场景验证真实种子的生成与消费链路；其他用例不再为相同前置过程付出完整成本。
- 对慢用例区分收集、准备、目标执行和清理时间。磁盘成为瓶颈时，先追查哪些夹具在重复扫描环境、复制仓库或初始化数据库，以及哪些写入真正参与被测断言。优先缩小副本到实际使用的文件和数据，并复用已校验且在本轮执行中不变的准备结果。
- 先消除重复工作，再优化分组与并行。依据实测负载分组，避免新增文件持续堆积在一个兜底通道；保留有价值的进程内复用。
- 共用昂贵真实种子的文件按组参与成本平衡，避免跨进程重建同一基线；分组只影响调度，不替代自动发现或缩小执行集合。
- 区分必要持久化与重复副作用：首次发布、并发冲突和故障恢复保留真实落盘；相同内容的幂等重试应校验并复用既有结果，不重复写入和同步未使用的临时文件。
- 资源预算同时包含顶层通道、用例子进程和原生计算线程。更多并发不等于更快，需检查最长通道、排队及 I/O 成本。
- 默认离线、确定性执行，不访问真实 Tushare、Futu、Windows 服务或生产状态。测试用本地模拟服务须隔离并可靠关闭。
- 所有临时文件、夹具、缓存、日志和一次性治理记录放根目录 `.tmp/`；不写真实研究目录，不使用系统临时目录，不在 `docs/` 新建流水或归档目录。

## 5. 执行与结果复用

常规修改只运行覆盖受影响行为的最小集合及变更范围静态检查。使用仓库 `.venv` 和根目录
[conftest.py](../conftest.py)管理隔离工作区；具体模块入口见各模块 README。
实现、输入与执行条件未变化时复用本轮有效结果，不因提交、合并或推送重复测试。

用户要求完整回归时使用统一入口：

```powershell
.\scripts\test-all.ps1
```

具体分组、并发参数和日志布局由[执行脚本](../scripts/test-all.ps1)维护，指南不复制动态文件清单。
入口自动发现各模块测试文件，按最近逐文件耗时分组，默认最多 2 个进程；每份文件只进入一个分组，
并逐项核对收集清单与 JUnit 结果。计划、结果和成本记录保存在 `.tmp/test-regression/`。
代码字节码缓存在 `.tmp/pycache/regression/` 复用，由 Python 校验源文件失效；测试生成源码的缓存随运行清理。
增加并发前先确认瓶颈和实测收益；机械盘上的小文件写入与同步提交不按 CPU 核数扩并发。
当前入口包含 `--release-acceptance`、前端测试及 Ruff；直接运行 Pytest 默认排除 `release_acceptance`，两者范围不同。
调用需要子进程或本地 Git 的入口时，按运行环境取得所需权限；权限失败与业务断言失败分别报告。

完整回归核对实际执行结果，Python 参数按展开后的收集节点比对，前端以测试运行器的结果单独计数。回归结果须区分失败、跳过、取消及待办，遗漏或重复执行也须明确报告。批量治理验收时，再核对实际运行的节点是否承接了场景清单。
发生失败后修复根因，只补测修复的用例和受修复影响的必要范围；未受影响且仍有效的通过结果继续复用。
全仓结果与修复补测分别记录，不把补测耗时当成全仓耗时；修改影响超出原范围时扩大相关验证，而非机械重跑全部。

软件回归、真实发布包检查、真实研究复验和生产验收分别陈述，不互相替代。
实际发布包身份检查不等于重新执行历史策略研究；线上检查按 [PTE 运维手册](PTE_OPERATIONS.md)及用户授权进行。

## 6. 治理触发与完成标准

每次新增或修改测试时顺手检查准入、重复准备及失效场景；超出时间预算、最长通道明显增长、
同一行为需要多处测试同步改动或夹具故障引起大面积失败时，优先治理，不等月度集中清理。
同一批变更同时新增和淘汰场景时，在提交中说明风险与节点的净变化。发现新增用例需要再准备一套完整账户、冻结包或数据目录时，先判断它是否在验证该准备过程，再决定能否复用现有种子。

治理按成本排序推进：读取已有逐项记录，定位最昂贵准备和最长执行链，选择可减少真实工作的改动，
用受影响用例验证风险覆盖。没有有效耗时证据时安排必要测量，不凭节点减少量或局部加速推算全仓结果。

完成时分别给出两项结论：

1. **功能验收：** 关键风险仍有有效覆盖；删除理由明确；受影响测试通过；已授权的完整范围无未解释遗漏。
2. **效率验收：** 对应范围的端到端耗时满足第1章预算；前后范围、环境及成本变化可解释。尚未测量或仍超预算时，明确标记待验收或未达标。

两项均满足，才能宣称本次相应范围的测试治理完成。只改指南、只减少节点或只通过功能检查，不代表性能治理完成。
全仓效率结论必须来自获准的完整运行，不能由聚焦结果替代；不为凑多次记录额外启动全仓回归。
若用户只调整耗时预算，可用执行范围和计时条件仍适用的完整记录重新判定。保留原始运行记录，另记新预算及结论；入口阈值的变更做聚焦验证。

提交说明保留范围、关键取舍、功能结果和耗时结论；详细日志、分析及一次性报告留在 `.tmp/`。
历史记录通过 Git 查阅，指南只维护当前规则。
